> **录下来，秀出去**

> 用 Anker soundcore work 录音豆，开发一个从真实声音出发的新场景。你负责按下录音，它负责把声音交给你的代码——**接下来，这段声音能变成什么，由你决定**。

## 01 让声音真正被「听懂」

录音豆，是一台**等待被接入的录音设备**，也可以是一块能够**重新被定义的硬件起点**。声音从它进来，围绕不同场景，可以变成**一份文档、一张图、或者一段「活过来」的语音记忆**。

从设备本体出发继续延展，我们期待你，让它真正进入一个**具体的人、一个具体的空间、一件具体要完成的事**里，承担起新的角色。

### 官方给的典型用户

soundcore Work 面向需要频繁记录线下谈话的专业用户。**医生、律师和访谈工作者**是这类可穿戴录音产品最容易理解的典型用户：他们需要完整记录谈话，同时也需要把注意力留给眼前的人。

三个官方示例场景：

| 场景 | 描述 |
|---|---|
| **医生问诊** | 医生与患者交流时，将录音豆佩戴在衣领上，用来记录患者对症状、病史和现状况的描述。医生不需要一直低头打字，可以把注意力放在患者和诊疗本身。问诊结束后，再通过录音和转写内容回顾信息、整理记录 |
| **律师咨询** | 律师与客户进行咨询时，谈话中通常包含大量物、时间、事件和诉求，获得客户同意后，律师可以用录音豆完整交流，在important信息出现时做标记，凭依据录音与转写核对原件，减少只靠手写记这造成的遗漏 |
| **记者访谈** | 记者、播客创作者或研究人员进行面对面访谈时，可以把录音豆夹在衣领上，专心倾听并继续追问，受访者说出关键观点时，双击录音豆做标记。访谈结束后，通过转写快速查找相关段落，并回到原始音频核对引用 |

**注意：三个场景全部是「听人说话」。** 官方设想的是专业人士的语音记录，不是环境声或非语音事件。

## 03 竞争力拆解 —— 六个维度

原文：

> 作为出题方，我们判断一个作品有没有竞争力，**不是数功能数量、看技术栈复杂度**，而是看它在一系列产品设计决定上的表现：**选中了什么问题、怎样使用硬件、把声音转化成了什么，以及如何证明这些设计有用。**
>
> 以下六个维度，是我们评审时实际会看的方向，也是团队自评的镜子。

雷达图六个维度，每个分**基础表现 / 有竞争力的表现 / 更突出的表现**三档：

1. **场景价值**
2. **硬件与场景结合**
3. **产品创新**
4. **完成度与可靠性**
5. **演示与验证**
6. **下一代硬件启发**

### 官方给的示范作品（虚构示例，仅用于说明）

**「访谈书签」**——让记者在采访后，快速找到想引用的那句话，并核对它的上下文。

五步链路：

```
1 双击标记    访谈中听到值得引用的观点时，双击录音豆做标记
2 SDK 同步    录音结束后，App 通过 SDK 同步音频和标记
3 云端转写    标记附近的内容整理成「引用候选卡片」
4 候选卡片    含候选原话、录音位置和前后文
5 回听确认    点击回听、修正转写、确认引用，加入素材清单
```

原文补充：「引用候选」来自录音原文，AI 生成的概括单独标识。**SDK 支持录音文件同步和实时音频获取两种接入方式**，本示例选择在录音同步之后处理；云端实时处理需团队自行接入实现。

### 这个示范在六维上的自评（官方标注）

| 维度 | 档位 | 官方原话 |
|---|---|---|
| 硬件与场景结合 | **更突出** | 双击标记决定 App 优先展示哪些片段，硬件动作直接影响结果；访谈中无需拿起手机；待验证双击是否打断访谈、标记是否容易遗漏 |
| 产品创新 | **有竞争力** | 把标记、原文定位、上下文回听、引用确认连成完整流程，交付的是可核对的采访素材；需与「普通转写 + 搜索」对比，证明确实更方便 |
| 完成度与可靠性 | **有竞争力** | 同步、转写、定位、回听、修改、确认都能走通，转写错误可修正；标记偏晚、人名识别错误、同步失败等异常场景仍待补 |
| 演示与验证 | **基础** | 现场能直观看到硬件动作如何影响最终结果；但尚缺不同录音者的重复验证，以及与原有做法的对比证据 |
| 下一代硬件启发 | **基础** | 由「想引用 vs 想后追问」提出可区分标记的设想合理，但目前来自自我设想；需先证明用户确有区分需求，再讨论按键或触发方案 |

**这张自评表本身就是预赛文档「落地可行性」那一维的模板**——官方在示范：主动写出自己哪一档、还缺什么。

### 官方给的提升路径

> 如果继续提升竞争力，最值得优先做的：

> 1. 邀请目标用户完成一次找引用任务，与「录音转写后手动搜索」进行对比
> 2. 测试标记滞后时是否仍能找到完整句子

## 04 常见误区 FAQ

> 这些坑会直接让你白忙一场，提前看清楚。

八条，以下是已读到的：

### Q：我能不能只做界面、不接真实设备？

> **不行。** 作品必须**真正用到录音豆**——现演现场要新录一段声音，经过 SDK 自动获得。只做界面、不接真实设备，评分时直接排除。

### Q：产品概念可以是小程序或 Web 应用吗？

> 可以。产品概念面向小程序或 Web 端没有问题，但**现场 Demo 必须用可安装、可操作的 iOS / Android App** 把完整场景跑通——录音豆的官方 SDK 在移动端，真实采集与演示都要落在 App 上。

### Q：只调 API、不做完整业务流程可以吗？

> **不行。** 评委要看的是**端到端闭环**，不是单个接口 demo。从录音进来到产出结果，整条链路要能跑通。

### Q：会议摘要 / 转写 / 聊天机器人方向能做吗？

> **不建议。** 只换一个提示词的会议摘要、转写或聊天机器人会被**直接排除**。我们想看的是录音之后帮你完成一件以前很麻烦的事。

## 对 PRX 的直接含义

### 强化的判断

1. **「会议摘要/转写」被官方写进常见误区，措辞是「直接排除」** —— 此前调研的红海判断从推测升级为官方明文。同赛道 T-047（IRIS，Research and Index System）如果落在转写+RAG 上，风险很大。
2. **端到端闭环是硬要求** —— 「只调 API、不做完整业务流程」不行。这与之前打法手册里「演示要完整链路」的判断一致。
3. **硬件不可替代性是明确考核项** —— 「硬件与场景结合」是六维之一，官方示范里特意强调「硬件动作直接影响结果」。听诊器方向的「为什么必须是这颗豆子」正对这一维。

### 新出现的硬约束

4. **现场必须用可安装、可操作的 iOS / Android App** —— 这条此前未知。意味着**必须有移动端**，纯 Python 服务端 + 网页不够。这直接抬高了 Android 那条线的优先级。
5. **现场必须新录一段声音** —— 不能放预录素材。听诊器方向的现场示教演示正好满足；但要求设备、App、检测链路当场全通。
6. **SDK 支持「录音文件同步」和「实时音频获取」两种接入方式** —— 官方明文承认实时流存在，与我们从 Demo 代码反推的结论一致（`acquireRealtimeAudioData`）。

### 需要重新权衡的

7. **官方的典型用户全是「听人说话」**（医生/律师/记者），示范作品也是访谈场景。听诊器方向「听机器不听人」是**偏离官方设想的**。这既是差异化机会，也意味着要多花篇幅论证场景价值——评委的默认心智在人声场景。
8. **「下一代硬件启发」是六维之一** —— 此前完全不知道有这一维。作品需要对硬件本身提出改进设想（如「可区分的标记按键」），且官方提醒：**要先证明用户确有需求，再讨论按键或触发方案**，不能是自我设想。
