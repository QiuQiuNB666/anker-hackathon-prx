## 从哪开始读

**要动手** → [prototype/README.md](prototype/README.md)，一条命令跑自检。

**要决策** → `docs/02-调研/打法手册.html`，第 01 节「硬约束」能直接判掉一批想法，第 04 节是三个方向的对比。

**要接设备** → `docs/04-决赛/SDK接入清单.md`，选 Android（iOS Demo 的实时回调是空函数），手机不解码、160 字节 Opus 包直接 WebSocket 转发给 Python。

**要写预赛文档** → `docs/01-官方材料/预赛材料模板.md` 是骨架，`打法手册.html` 第 08 节是每个评审维度的写法。

## 现在的状态

- **方向**：智能录音赛道，两个候选。《听诊器》——让录音豆听机器不听人，非语音声学是品类真空。《防霸凌求助按钮》——团队 9/10 提出。两轮调研后**降级为备选**：事中触发不成立（38 秒事件、强直性不动、亮灯等于递给对方），事前例行开启只覆盖受害者 11–19%，事后标记不需要录音硬件；亮灯设备威慑零证据、激怒有证据。两份定型文档均在 `docs/02-调研/`。
- **原型**：下游管线已跑通（合成信号上分离度 8.1×，Opus 16k 压缩后保留 93%）。不依赖录音豆，10/16 只需把输入源从麦克风换成设备。SDK 核实后确认设备原生就是 Opus 16kHz，与原型采样率一致，且有实时分片回调——分段拉取的延迟约束不成立，可做近实时。
- **待办**：见下。
